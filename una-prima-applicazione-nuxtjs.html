    3.2. Descrizione della struttura ad albero di un’applicazione [nuxt]

    Riprendiamo la struttura ad albero dell’applicazione creata:

    Il ruolo delle cartelle è il seguente:

    assets
    risorse non compilate dell'applicazione (immagini, ...);
    static
    i file di questa cartella saranno disponibili nella directory principale dell’applicazione. In questa cartella si inseriscono i file che devono trovarsi nella directory principale dell’applicazione, come ad esempio il file [robots.txt] destinato ai motori di ricerca;
    components
    i componenti [vue] dell’applicazione utilizzati nei file [layouts] e [pages];
    layout
    i componenti [vue] dell’applicazione che fungono da layout per i [pages];
    pagine
    i componenti [vue] visualizzati dai diversi percorsi dell’applicazione. Si potrebbero definire le viste dell’applicazione. Le pagine svolgono un ruolo particolare in [nuxt]: i percorsi vengono creati dinamicamente a partire dalla struttura ad albero presente nella cartella [pages];
    middleware
    gli script eseguiti ad ogni cambio di route. Consentono di controllarle;
    plugin
    ha un nome che può creare confusione. Può contenere plugin ma anche script classici. Gli script presenti in questa cartella vengono eseguiti all’avvio dell’applicazione;
    store
    se contiene uno script [index.js], quest'ultimo definisce un'istanza dello store di [Vuex];

    Se una cartella è vuota, è possibile eliminarla dalla struttura ad albero. Nell’esempio sopra riportato, le cartelle [assets, static, middleware, plugins, store] e [2] possono essere eliminate.

    3.5. La cartella [pages]

    La cartella [pages] contiene le viste instradate, ovvero quelle visibili all’utente. La pagina [index.vue] è la pagina iniziale dell’applicazione. Per [nuxt.js] non è presente alcun file di instradamento. I percorsi vengono determinati in base alla struttura della cartella [pages]. In questo caso, la presenza di un file [index.vue] creerà automaticamente un percorso denominato [index] e un percorso [/index] ridotto a [/], poiché si tratta della pagina iniziale. Viene quindi creato il seguente percorso:

            { name : ‘index’, path : ‘/’}

    3.8. Modifica della pagina iniziale

    Modificheremo il file [index.vue]. Nella nostra installazione del progetto, abbiamo installato due dipendenze:

    • [eslint]: che verifica la sintassi dei file JavaScript e dei componenti Vue. Se è stata installata l’estensione [ESLint] di VSCode, la sintassi viene verificata durante la digitazione del testo e gli errori vengono segnalati immediatamente;
    • [prettier]: che formatta i codici JavaScript in modo standard;

    Queste dipendenze sono registrate nel file [package.json]:

    
"devDependencies": {
    "@nuxtjs/eslint-config": "^1.0.1",
    "@nuxtjs/eslint-module": "^1.0.0",
    "babel-eslint": "^10.0.1",
    "eslint": "^6.1.0",
    "eslint-config-prettier": "^4.1.0",
    "eslint-plugin-nuxt": ">=0.4.2",
    "eslint-plugin-prettier": "^3.0.1",
    "prettier": "^1.16.4"
}

    Ho notato (novembre 2019) che con l’installazione effettuata tramite il comando [yarn create nuxt-app], gli strumenti [eslint, prettier] non funzionano durante la digitazione dei testi. Gli errori vengono segnalati solo in fase di compilazione. Dopo alcune ricerche, ho trovato una configurazione che funziona:

    Si installa nella directory principale del progetto una cartella denominata [.vscode] contenente il seguente file [settings.json]:

    
{
  "eslint.validate": [
    {
      "language": "vue",
      "autoFix": true
    },
    {
      "language": "javascript",
      "autoFix": true
    }
  ],
  "eslint.autoFixOnSave": true,
  "editor.formatOnSave": false
}
    • righe 2-11: indicano che quando [eslint] convalida i file .vue e .js, deve correggere gli errori che è in grado di correggere;
    • riga 12: quando un file viene salvato, [eslint] deve correggere gli errori che è in grado di correggere;
    • riga 13: disabilita la formattazione predefinita in VSCode al momento del salvataggio. Sarà [prettier] a occuparsene;

    Con questa configurazione:

    • gli errori di sintassi o di formattazione vengono segnalati non appena si digita il testo;
    • gli errori di formattazione vengono corretti automaticamente al momento del salvataggio del file;

    La libreria [prettier] viene configurata dal file [.prettierrc]:

    Questo file è, per impostazione predefinita, il seguente:

    
{
  "semi": false,
  "arrowParens": "always",
  "singleQuote": true
}
    • riga 1: nessun punto e virgola alla fine delle istruzioni;
    • riga 2: se una funzione «freccia» (arrow) ha un unico parametro, questo è racchiuso tra parentesi;
    • riga 3: le stringhe di caratteri sono racchiuse tra apostrofi (non tra virgolette);

    Aggiungiamo le due regole seguenti:

    
{
  "semi": false,
  "arrowParens": "always",
  "singleQuote": true,
  "printWidth": 120,

    Perché due visualizzazioni e non una sola?

    Un’applicazione [nuxt] si compone di due elementi, un server e un client:

    1. il server fornisce le pagine dell’applicazione all’avvio della stessa e poi ogni volta che una pagina viene aggiornata nel browser (F5) oppure quando l’utente digita manualmente un URL dell’applicazione;
    2. ogni pagina fornita dal browser contiene la pagina richiesta e il codice JavaScript dell’intera applicazione, che viene poi eseguito nel browser. Questo è il client. Finché non viene effettuato un aggiornamento della pagina nel browser, l’applicazione funziona come una classica applicazione Vue in modalità [sap] (Single Page Application). Non appena l’utente provoca manualmente un aggiornamento della pagina, questa viene richiesta al server e si ritorna alla fase 1 precedente.

    Ciò che occorre comprendere è che si tratta delle stesse pagine della cartella [pages] fornite sia dal server che dal client. Per questo motivo, gli sviluppatori di [nuxt] definiscono questo tipo di pagine “pagine isomorfe”. Le stesse pagine [.vue] possono essere interpretate sia dal client che dal server. Prendiamo ad esempio la pagina [index]:

    
<template>
  <div class="container">
    <div>
      <logo />
      <h1 class="title">
        nuxt-intro
      </h1>
      <h2 class="subtitle">
        nuxt-intro
      </h2>
      <div class="links">
        <a href="https://nuxtjs.org/" target="_blank" class="button--green">
          Documentation
        </a>
        <a
          href="https://github.com/nuxt/nuxt.js"
          target="_blank"
          class="button--grey"
        >
          GitHub
        </a>
      </div>
    </div>
  </div>
</template>

<script>
/* eslint-disable no-console */
import Logo from '~/components/Logo.vue'

export default {
  components: {
    Logo
  },
  // ciclo di vita
  created() {
    console.log('created, route=', this.$route)
  }
}
</script>

    Trattandosi della pagina iniziale, all’avvio dell’applicazione viene fornita dal server. Anche la pagina sul server ha un ciclo di vita, identico a quello di una pagina [Vue] classica, tranne che per le funzioni [beforeMount, monted] che non esistono sul lato server. La funzione [created] viene eseguita, il che spiega il primo log. Ciò significa, tra l’altro, che il server è in grado di eseguire script JavaScript. In questo caso, e in generale, si tratta di un server [node.js]. Una volta creata la pagina sul server, questa arriva al browser dove viene nuovamente sottoposta al ciclo di vita. La funzione [created] viene eseguita una seconda volta, il che genera il secondo log.

    L’architettura di un’applicazione [nuxt] potrebbe essere la seguente:

    • [1]: il browser che ospita l’applicazione [nuxt] una volta che questa è stata caricata sul browser. È ciò che viene definito il client [nuxt];
    • [3]: il server che ospita inizialmente l’applicazione [nuxt]. Quest’ultima viene caricata sul browser [1] all’avvio dell’applicazione e ogni volta che l’utente aggiorna la pagina corrente del browser o digita manualmente un URL dell’applicazione. È qui che risiede la differenza di funzionamento rispetto a un’applicazione Vue classica. Con quest’ultima, una volta caricata sul browser, il server non veniva più interpellato in seguito. Un’altra differenza importante che per ora non abbiamo potuto osservare è che il server di un’applicazione Vue è un server statico, incapace di interpretare le pagine [.vue], mentre quello di un’applicazione Nuxt di tipo [universal] è un server JavaScript. Prima di inviare una pagina al browser, il server può eseguire script e, ad esempio, recuperare dati dal server [2];
    • [2]: è il server che fornisce dati sia ai client [nuxt] e [1], sia ai server [nuxt] e [3];

    Nello schema sopra riportato si possono distinguere tre sottosistemi client/server:

    • [1, 3]: ospita l’applicazione [nuxt]. [3] la fornisce all’avvio dell’applicazione con la pagina iniziale e ogni volta che l’utente richiede manualmente una pagina. [1] ospita l’’applicazione [nuxt] ricevuta da [3], che a sua volta funziona in modalità [SAP] finché le pagine non vengono richieste manualmente a [3];
    • [1, 2]: in modalità [SAP], il client [nuxt] recupera dati esterni da uno o più server;
    • [3, 2]: durante la generazione della pagina richiesta dall’utente, anche il server [3] può recuperare dati esterni da uno o più server;

    È quindi il server [3] a distinguere un’applicazione [nuxt] da un’applicazione [vue]. Questo server viene interpellato ogni volta che l’utente richiede manualmente una pagina. Esso elabora le stesse pagine [.vue] del client [vue] e [1]. Si tratta di un server JavaScript in grado di eseguire gli script presenti nella pagina. Ciò può modificare, ad esempio, il modo in cui viene generata la pagina iniziale con dati esterni: mentre un’applicazione [vue] ottiene tali dati necessariamente dal client [1], qui possono essere recuperati dal server [3] prima che la pagina venga inviata al client. La pagina iniziale acquista così rilevanza e può contribuire a migliorare il SEO dell’applicazione.

    Nota: in modalità sviluppo, le tre entità [1, 2, 3] si trovano spesso sulla stessa macchina. Questo sarà il caso in tutti i nostri esempi.

    3.11. Configurazione di un server sicuro

    Come indicato sopra, l’URL dell’applicazione è [http://192.168.1.128/nuxt-00/]. Vorremmo che fosse [https://192.168.1.128/nuxt-00/]. Dobbiamo quindi creare un server sicuro. Vi mostriamo come procedere.

    Nota: il metodo è stato tratto dall’articolo [https://stackoverflow.com/questions/56966137/how-to-run-nuxt-npm-run-dev-with-https-in-localhost].

    Per prima cosa creiamo una chiave privata e una chiave pubblica con [openssl]. [openssl] viene normalmente installato insieme al server Laragon. Di conseguenza, questo comando è disponibile in qualsiasi terminale Laragon. Apriamo quindi un terminale Laragon e posizioniamoci nella cartella dell’applicazione distribuita:

    • in [2], si digita il comando [openssl genrsa 2048 > server.key];
    • in [3], viene creato un file [server.key];
    • in [4], si digita il comando [openssl req -new -x509 -nodes -sha256 -days 365 -key server.key -out server.crt];
    • in [5], viene creato un file [server.crt];

    Questi due file costituiscono un certificato autofirmato. La maggior parte dei browser li accetta solo previa approvazione dell’utente che ha richiesto la pagina.

    I file [server.key, server.crt] devono ora essere utilizzati dall’applicazione web. A tal fine, il file [nuxt.config.js] deve essere modificato come segue:

    
import path from 'path'
import fs from 'fs'

export default {
  // router
  router: {
    // radice dei URL dell'applicazione
    base: '/nuxt-00/'
  },
  // server
  server: {
    // porta di servizio, 3000 per impostazione predefinita
    port: 81,
    // indirizzi di rete in ascolto, per impostazione predefinita localhost: 127.0.0.1
    // 0.0.0.0 = tutti gli indirizzi di rete del computer
    host: '0.0.0.0',
    // certificato autofirmato
    https: {
      key: fs.readFileSync(path.resolve(__dirname, 'server.key')),
      cert: fs.readFileSync(path.resolve(__dirname, 'server.crt'))
    }
  }
}

    Sono le righe 18-21 che implementano il protocollo [https].
